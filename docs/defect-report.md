# 缺陷报告：客户端断连恢复改造未达预期（已知缺陷，未解决）

> **状态：已知缺陷（Known Defect），不作为已解决问题**
> **r2 修复（锁竞态）已提交，待真机验证；验证通过前仍记为未解决。**
> 版本：dsh-duet 0.1.10（客户端改造）
> 日期：2026-11-04
> 关联：PR #5（duet-guard 连接守护）、PR #6（记忆边界分析）

## 一、问题描述与复现路径

### 现象

在部署客户端断连恢复改造（resultResume 持久化、自动重连、跨 epoch 续传）后，**语音连接仍然出现断开**；断开后**未观察到自动恢复迹象**——按钮未回到已连接状态、语音未继续，需要手动重开。

### 复现路径

1. 打开 DSH Desktop 的 Web 页面，选择一个 workspace；
2. 点击麦克风开启**交互模式**（或喇叭开启**播报模式**）；
3. 保持连接并持续对话 4~10 分钟（实测上游在 p50≈275s、p90≈523s 触发重置）；
4. 观察：连接断开；预期在 2s 退避后自动重连，**实际未恢复**。

### 判定

| 项 | 结论 |
|----|------|
| 断连本身 | 上游 `duet-router-acc` 每 4~10 分钟强制重置（服务端行为，客户端无法阻止） |
| 自动恢复 | **未生效**（实测无恢复迹象） |
| 整体结论 | 改造只降低了断连影响/概率，**未彻底解决**问题，记为已知缺陷 |

## 二、已尝试的修复方案及其局限

### 方案 A：duet-guard 浏览器守护（PR #5）

- **做法**：5s 扫描 + MutationObserver，UI 层判定断连后点击重连，指数退避 2s→30s；
- **局限**：
  - 仅同构 DOM 夹具测试，未真机端到端（PR #5 自述）；
  - 依赖 DOM 选择器，插件改版即失效；
  - 只做 UI 层兜底，无法恢复服务端 epoch 变化导致的上下文丢失。

### 方案 B：客户端 resume/自动重连改造（本 PR）

- **做法**：
  1. `resultResume`（epoch/cursor）持久化到 localStorage；
  2. `close()` 只在 user_off / unmount / page_unload 时清除 resume；
  3. `harness_sync` 的 `offer()` 跨 epoch 续传 cursor；
  4. 1006/1011 自动重连（2s→30s，最多 5 次）+ 重连后强制同步。
- **实测结果**：**连接仍断开，且未观察到自动恢复**。
- **根因定位（2026-11-04，代码审查 + trace 取证）**：
  - trace 显示上游固定 `1006`、浏览器收到 `1011`，两码均命中旧版自动重连条件 → 排除「关闭码不匹配」；
  - 运行中的服务已确认返回含改造的客户端代码（`/duet/assets/client/browser.mjs` 含 `autoReconnectAttempts`）→ 排除「文件未替换」；
  - **高概率根因：`navigator.locks` 释放竞态**——旧连接 `close()` 里 `release()` 只是 resolve 持有 Promise，锁的真正释放发生在后续微任务；重连时立即 `ifAvailable:true` 会拿到 `null`，被误判为 `voice_tab_in_use` → 直接 `fail` → `setMode('off')`，于是「毫无恢复迹象」。
- **其余假设与状态**：

| # | 假设 | 状态 |
|---|------|------|
| a | 客户端未加载新代码 | 已排除（服务端返回新代码；页面仍需刷新才生效） |
| b | close code 不匹配 | 已排除（1006/1011 均在条件内） |
| c | mode 已被错误路径置 off | 已纳入 r2 修复（先恢复 mode 再重连） |
| d | 上游 flapping | 待观察（r2 会记录每次尝试） |

### r2 修复（已提交，待真机验证）

1. **锁获取重试**：`acquireVoiceLock` 5 次 × 150ms，消除释放竞态导致的 `voice_tab_in_use`；
2. **重连触发扩大**：除正常关闭 1000 / 容量 1013 外，任何异常关闭都重连；
3. **mode 恢复**：若被错误路径提前置 off，先恢复原模式再重连；
4. **尊重用户意图**：用户主动关闭 / 页面卸载时作废待执行的重连；
5. **断连诊断暂存**：断连期间诊断入内存队列，重连成功后随首个 WS 回传（宿主 trace 可取证）；
6. **客户端版本标记**：`duet-client-r2-auto-reconnect`，用于确认实际加载版本；
7. **UI 可见提示**：断开时提示「正在自动重连（第 N 次）…」。

- **本质局限**：仍无法阻止服务端 4~10 分钟重置。

### 共同局限

两个方案都在客户端/UI 层；服务端主动重置无法被阻止，自动恢复只能压缩窗口，不能消除断连。

## 三、后续建议（含需要上游配合的改动）

### 客户端侧（本仓库可做）

1. ✅ **确认新代码已加载**：已加版本标记 `duet-client-r2-auto-reconnect`；
2. ✅ **扩大自动重连触发条件**：除 1000/1013 外全部重连，并记录 close code；
3. ✅ **修正状态机**：重连前若 mode 被置 off，先恢复原 mode；
4. ✅ **遥测**：断连诊断暂存并在重连后回传，形成可验证链路；
5. ⏳ **host 端 proxy 连接迁移**：上游重置时预建新连接、浏览器侧无感切换（待做）。

### 上游侧（duet 服务端，需作者配合）

1. **调大连接时长上限 / keep-alive**：≥30 分钟，或推流期间不触发时长上限；
2. **提供 `realtime_v2` 直连/自建说明**：允许用户自建稳定端点；
3. **网关层连接迁移/预重连**：让浏览器侧无感切换；
4. **暴露连接状态事件/心跳**：便于客户端准确判定，而不是靠读 DOM 或猜测 close code。

## 附：验证标准

修复有效的判定标准：

- 连续 30 分钟语音对话，期间发生 ≥3 次上游重置；
- 每次断开后 **5s 内自动恢复**，且上下文（epoch/cursor）不丢；
- 全程无需用户手动重开。
