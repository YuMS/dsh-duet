# 语音意图路由反馈：交互语 vs 落笔语，需要一个显式区分点

> 来自实际使用反馈，非代码缺陷报告。目标：让「和语音助手说话」与「让助手把话写进输入框」不再互相误伤。

## 1. 现象

日常使用中有两类 utterance：

- **落笔语**：「输入，帮我整理这周计划」「把这句话改成下周版本」——期望内容进入输入框；
- **交互语**：「你好」「刚才那个为什么失败」「你先别发，我改一下」「这句说得不对吧」——期望只是对话，不该动输入框。

实际表现是边界不稳：交互语被当成落笔内容写进输入框；反过来，明确要给的内容又被当成闲聊消化掉。结果是用户要么删掉误写的内容，要么重新说一遍指令，对话不"丝滑"。

## 2. 根因假设（基于 README 与可观察行为）

README 里目前的语音操作是**指令词路由**：命中「输入 / 发送 / 切换 / 新建…」等动词短语才执行动作。这套路由能覆盖显式指令，但缺三样东西：

1. **没有意图分类 + 置信度**：一句话要么命中指令词，要么落到自由聊天，中间没有"拿不准"的档位；
2. **没有"编辑态 / 对话态"的状态区分**：输入框是否处于"我正在写"的状态，不参与路由决策；
3. **没有落笔前的确认与撤回**：写错了只能手动删。

所以问题不完全是"模型理解能力"，更像是**路由策略缺少一个显式的区分点**：交互语与落笔语在语言形式上本来就有系统性差异，可以显式建模。

## 3. 建议：把区分点显式化

### 3.1 语言形式上的可判别信号

| 信号 | 偏交互语 | 偏落笔语 |
|---|---|---|
| 句式 | 疑问、感叹、评价、纠正（"不对""等一下"） | 祈使 + 明确动词（"输入/写成/改成/发出去"） |
| 指代 | "你""刚才""这个"指向助手或上一轮 | "这段""标题""正文"指向文档对象 |
| 时态/语气 | 现在进行、协商、试探 | 完成式、交付式（"给我""整理成"） |
| 长度与结构 | 短、口语、无标点结构 | 有成段内容、列举、引号包裹 |

这些不是硬规则，但足以作为分类特征，比单一关键词命中稳。

### 3.2 三档路由（关键改动）

- **高置信落笔** → 直接写；
- **中置信** → 不进输入框，先用一句话复述确认：「要我把这句写进输入框吗？」用户说"对/写"再落笔；
- **低置信 / 交互语** → 只对话，不动输入框。

现在缺的是中间那档，导致二元判断必然在边界上翻车。

### 3.3 编辑态状态机

引入两个状态：`idle`（对话态）与 `composing`（编辑态）。

- `idle` 下默认**不写**输入框，只有高置信落笔语或用户确认才进入 `composing`；
- `composing` 下才允许"把这周改成下周"这类就地修改；
- 用户说"取消""算了""别写了"→ 回 `idle`，已写内容保留但不追加。

### 3.4 可撤销

落笔后若干秒内（建议 5s）支持「撤掉刚才那句」，把误写成本从"手动删"降到一句话。

### 3.5 可观测（便于调参）

把每次路由决策记进现有诊断通道：`{intent, confidence, target, reason}`。作者据此看误判集中在哪类句式，比凭感觉调提示词有效。

## 4. 验收标准（可测）

用 10 条对照语料回归，每条标注期望动作（write / chat / confirm）：

- 交互语误写率 < 5%
- 落笔语漏写率 < 5%
- 中置信场景 100% 走确认，不静默落笔
- 撤销指令在 5s 窗口内 100% 生效

## 5. 说明

这条反馈来自"用起来不顺"的体感，不是对模型的否定：全双工场景下边说边改，本来就比一问一答更容易踩边界。把"交互"与"落笔"做成显式状态与三档路由，收益会比继续堆提示词更大。
